## 1. 数据模型：一条铁律和三个坑

> **数据模型细节以 `CONTEXT.md` 当前版为准。** 本节只讲代码怎么写；字段结构、取值与口径冲突时，一律以 `CONTEXT.md` 为准。

`CONTEXT.md` 里已经写死了词汇定义，这里只说**代码怎么写**。

**铁律：一条记录 = 游戏里的一个物品。不是"一个物品的两种吃法"。**

- `Hot Dog` 生吃熟吃 → **一条**，生熟数值都在 `attributes.statuses.raw` / `.cooked` 里
- `Cooked Bird` → **独立的一条**（它在游戏里本来就只能从 `Big Egg` 开出熟的）
- 所以**不要**做"采集时给每个食物生成两条"这件事。数据源里根本没有熟食的独立页面，硬拆只会造出一堆空条目。

**坑 1（必踩，我第一次用 MyBatis-Plus 也踩）：`JacksonTypeHandler` 会静默失效。**

```java
@Data
@TableName(value = "t_item", autoResultMap = true)   // ← autoResultMap 漏了就永远是 null
public class Item {
    @TableField(typeHandler = JacksonTypeHandler.class)
    private ItemAttributes attributes;               // JSON 列 → 对象
}
```

漏了 `autoResultMap = true` 的后果是：**查出来的 `attributes` 永远是 null，而且不报错。** 你会以为是数据没灌进去，去查数据库，数据好端端在那儿。这个 bug 能吃掉你半天。

**坑 2：JSON 列用 MySQL 原生 `JSON` 类型，不要用 `TEXT`。** `JSON` 类型写入时校验格式，写错**当场抛异常**；`TEXT` 把脏数据静默存进去，等到演示时小程序白屏才发现。

**坑 3：`weight` 是负数有意义的值，不是"重量"。** 实测取值范围 `{-15, -2.5, -5, 0, 2.5, 5, 7.5, 10, 12.5, 40}`。用 `DECIMAL(5,1)`，**不要用 Integer**（现有 `Item.java` 就是 Integer，要改）。语义待确认就按原值存，别自己取绝对值。

**`attributes` 的 JSON 结构（`resul.md` 10.4 定的，照这个来）：**

```json
{
  "statuses": {
    "raw":    { "hunger": -30, "bonus": 20 },
    "cooked": { "hunger": -60, "bonus": 30 }
  },
  "biomes": ["Gloom"],
  "sources": ["Campfires"],
  "locations": [],
  "cookingNotes": "…",
  "description": "…"
}
```

> `cooked` 里存的是**总量**（数据源的公式：熟食饱食总量 = Hunger × 2、加成总量 = Bonus × 1.5）。展示时要显示"增量"就**在前端减一下**，不要库里存两份。

## 4. 接口契约（Sch 冻结，CRQ 只读这个）

**这份契约冻结在第 5 天。改动必须当面通知对方。**

统一响应包：

```json
{ "code": 0, "msg": "ok", "data": {} }
```

`code`: 0 = 成功，401 = 未登录，4xx/5xx = 失败。

| 方法 | 路径 | 用途 | 备注 |
|---|---|---|---|
| GET | `/api/items` | 列表 | 参数：`primaryType`、`tag`、`biome`、`keyword`、`page`、`size` |
| GET | `/api/items/{slug}` | 详情 | 返回含 `attributes`，生熟都在里面 |
| GET | `/api/items/search?keyword=` | 搜索 | 可按 `name_en` / `name_zh` 搜 |
| GET | `/api/tags` | 筛选用的标签字典 | 给筛选面板渲染用 |
| GET | `/api/biomes` | 生态字典 | 同上 |
| POST | `/api/auth/login` | 小程序登录 | body 传 `js_code`，返回 token |
| POST | `/api/ai/chat` | AI 对话 | body 传 `question`；key 由用户提供 |

**列表项返回结构（CRQ 按这个写渲染，**不要依赖数据库 JSON 原样透传**）：**

```json
{
  "slug": "hot-dog",
  "nameEn": "Hot Dog",
  "nameZh": "热狗",
  "icon": "https://…/hot-dog.png",
  "primaryType": "FOOD",
  "rarity": null,
  "weight": -5.0,
  "isCookable": true,
  "tags": ["NATURAL_FOOD"]
}
```

> **为什么不让 JSON 列直接透传**：小程序有**版本碎片**问题（用户不会主动更新，老版本会长期存在）。数据库字段可以随便加，但**接口响应结构必须有稳定契约** —— 否则你哪天改个 JSON 里的 key，老版本小程序就白屏了。这一条本身就是个能讲的技术点。
