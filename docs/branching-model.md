# 分支模型与团队约定

这是全组共同的规矩。**每个成员都应该读完这一页。**

---

## 一、三条线

| 分支 | 用途 | 谁动它 |
|---|---|---|
| `main` | **稳定线。** 只放能跑通的完整版本。 | 组长，并且只在里程碑时更新 |
| `dev` | **集成线。** 所有人的成果都汇总到这里，日常协作的中转站。 | 所有人（通过合并自己的分支） |
| 个人分支 | **每人一条**，各写各的。名字用拼音，比如 `laowang`、`xiaoLi`。 | 只有你自己 |

**为什么要分三条线？**
如果四个人都直接在 `main` 上改，任何一个人写崩、提交了跑不通的代码，
**其他三个人的工作全部受牵连**。分线的本质是：*让「写代码」和「代码合格」这两件事分开*。

---

## 二、铁律

1. **推送之前，先拉取。**
   这是唯一一条没有例外的规则。不先拉，你的推送会被拒绝；更糟的情况是覆盖掉别人刚推上去的东西。

2. **只做新增，不改别人的文件。**
   你负责你自己的模块。看到别人的代码有问题，在群里说出来，让别人改，别自己动手。

3. **永远不点 `Force push`。**
   它会用你的版本**抹掉**远程已有的提交。这是破坏性的，不是解决冲突。

4. **合并的方向不能搞反。**
   合并的意思是"把**别的分支**并进**我现在站在的分支**"。
   想把自己的代码并进 `dev`，**必须先切到 `dev`**，再执行合并。
   菜单会写成 `Merge '你的分支' into 'dev'` —— **念一遍它，念不通就是反了**。

## 三、每个人的日常循环

| 什么时候 | 做什么 | IDEA 位置 |
|---|---|---|
| 每天开工前 | 切回自己分支，把 `dev` 的更新并进来 | 分支控件 + `Ctrl+T` |
| 写代码时 | 确认右下角是**你自己的分支**，不是 `dev` 也不是 `main` | 右下角分支控件 |
| 写完一小块 | 提交，写清楚这次做了什么 | `Alt+0` → Commit |
| 提交后 | 推送到你自己的分支 | `Ctrl+Shift+K` |
| 要给大家用 | 切到 `dev` → 拉取 → 合并自己的分支 → 推送 `dev` | 见下方「合并三步」 |

### 合并三步（最关键的一段）

1. **切到 `dev`** —— 右下角分支控件 → 选 `dev` → Checkout
2. **先拉取** —— `Ctrl+T`。不做这步，后面必然出问题
3. **合并自己的分支** —— 再点右下角分支控件 → 找到自己的分支 → `Merge '你的分支' into 'dev'`

合并完成后，**切回自己的分支，把 `dev` 也并进来**，保持一致。最后推送。

> **切错分支是新手翻车第一名。**
> 合并前**务必看一眼右下角**。站在 `dev` 上合并自己的分支 = 正确；
> 站在自己的分支上合并 `dev` = 方向反了，`dev` 上什么都不会变，你会以为"代码丢了"。

## 四、分支与文件命名

| 类型 | 规则 |
|---|---|
| `main` / `dev` | 固定，不要重命名 |
| 个人分支 | **拼音或英文**，如 `laowang`、`xiaoLi` |
| 文件名 | **也用英文/拼音** |

> **不要用中文做分支名和文件名。**
> 中文名在 Windows、Mac、Linux 之间会出现编码乱码，`git` 会抛出看不懂的错误。
> **这条不是风格问题，是能不能跑的问题。**

---

## 五、提交信息怎么写

| ✗ 别这样 | ✓ 这样 |
|---|---|
| `aaa` | `完成题库列表页` |
| `修改` | `修复登录后跳转失败` |
| `123` | `新增 Guide 实体类` |
| `。。。` | `补充 README 的接口说明` |

一句话说清"这次改了什么"。这东西以后是你和队友唯一能看懂的历史记录。

---

## 六、出问题时

| 现象 | 第一反应 |
|---|---|
| 推送被拒绝（`Push rejected`） | **先拉取**，别点 Force push。原因几乎总是"远程有你没有的东西" |
| 合并时提示冲突（conflict） | 正常现象，不是你的错。**别慌，别删文件**，停下来问组长 |
| 右下角的 `dev` 没有别人的新代码 | 你还没拉取。按 `Ctrl+T` |
| 不确定自己在哪条分支上 | **先看右下角。** 在不确定的时候做任何操作，都是在赌 |
| 实在搞不定了 | 在群里喊组长。**不要自己乱试"能不能修好"** —— 乱试才是真的把代码搞丢的方式 |

---

## 七、分工比技巧重要

Git 能解决技术上的撞车，但解决不了"两个人都在改同一个文件"这种**管理上**的撞车。

**趁项目还空，把模块分清楚**：谁负责哪几个包、哪几个文件。
这一条做对了，你们后面几乎不会遇到冲突。

---

**这份约定为什么重要**
四人小组最容易出的事，不是技术难，而是**撞车**：两个人改了同一个文件，一个人不知道另一个人的改动，
最后谁也不知道该信哪份代码。上面这些规则全部是为了一件事：
**让每个人的工作互不干扰，又能安全地汇到一起。**
