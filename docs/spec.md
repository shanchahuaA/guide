# PEAK 图鉴小程序 —— 项目规格

> 这是 `/to-spec` 产出的**正式规格**，写给验收方和协作者看。
> 日常执行排期见 `docs/分工与目标清单.md`（那份是给干活的人看的口语版）。

## Problem Statement

PEAK 是一款合作攀岩游戏，游戏**内部没有图鉴**。玩家想知道"这个浆果有什么用""这个道具去哪找""生吃熟吃差多少"时，只能去英文社区 Wiki（`peak.wiki.gg`）翻网页。

这带来三个具体困难：

- **语言门槛**：Wiki 是英文的，中文玩家看不懂物品效果。
- **翻页成本高**：想知道一个物品的完整信息要读完一整页散文，而且物品散落在多个交叉分类里（一个浆果同时属于 `Food`、`Natural food`、`Berry`）。
- **生熟对比无处可查**：游戏里"把食物拿到火上烤"是最常见的操作，但熟食数值在 Wiki 上不是现成字段，是模板实时算出来的，**没有一处能直接看到"生 vs 熟"对比**。

玩家需要的是：**掏出手机，搜一个物品，一屏看到它的全部信息，包括生熟对比。**

## Solution

一个微信小程序图鉴，首期覆盖**食物**和**道具**两个模块，共 **130 条**条目（食物 48 + 道具 82）。

- 数据来自社区 Wiki 的结构化接口，经采集转换后落库，**中文展示**。
- 按**主类型**做一级导航（食物 / 道具），按**标签**（浆果、蘑菇…）和**生态**做二级筛选。
- 物品详情**一屏看完**：图标、名称、重量、标签、状态效果、**生熟对比**、描述、成就。
- 提供**关键词搜索**（中英文名都能搜）。
- 提供 **AI 对话**：图鉴内的问题由后端查自己的数据回答；**路线类问题**（"今日最佳路线"）联网在 B站 搜索当天日期的攻略并给出链接。
- 图鉴数据经 **Redis 缓存**，修正数据后立刻生效，不需要小程序重新发版。

这是一个**纯查询工具**：不记录收集进度，不做用户背包。用户随时来查、查完就走。

## User Stories

**浏览图鉴**

1. 作为玩家，我想打开小程序直接看到图鉴首页，以便不用登录就能开始查东西
2. 作为玩家，我想看到"食物"和"道具"两个一级入口，以便按我当下关心的类别进入
3. 作为玩家，我想在列表里看到每个物品的图标和名称，以便快速扫视
4. 作为玩家，我想列表能分页加载，以便滑动时不会一次性拉 130 条
5. 作为玩家，我想列表同时显示中文名和英文名，以便对照游戏里的英文界面
6. 作为玩家，我想看到每个物品的重量，以便判断带在身上的代价
7. 作为玩家，我想按标签筛选（只看浆果、只看蘑菇），以便按我需要的功能找东西
8. 作为玩家，我想按生态筛选（只在某个区域能找到的东西），以便在当前地图里找可用的物品
9. 作为玩家，我想多个筛选条件能同时生效，以便精确定位
10. 作为玩家，我想筛选条件可以清空，以便重新开始找
11. 作为玩家，我想按重量排序，以便挑最轻的带

**查看详情**

12. 作为玩家，我想点开一个物品看到它的完整信息，以便一次读完不用翻页
13. 作为玩家，我想在详情页看到**生吃和煮熟两栏数值并排对比**，以便决定要不要花时间烤
14. 作为玩家，我想在物品不可烹饪时**看不到熟食区块**（而不是看到一排 0），以便不被误导
15. 作为玩家，我想看到物品的全部状态效果（饱食、加成、中毒…），以便知道吃下去的后果
16. 作为玩家，我想看到带持续时间的效果有多久（中毒 10 秒），以便判断风险
17. 作为玩家，我想看到负面效果用负值或醒目的方式标出，以便不会看漏
18. 作为玩家，我想看到物品的获取来源（行李、雕像…），以便知道去哪找
19. 作为玩家，我想看到物品的图鉴描述，以便了解游戏背景
20. 作为玩家，我想看到与该物品相关的成就，以便知道还有什么可做
21. 作为玩家，我想看到物品的图标大图，以便在游戏里认出来

**搜索**

22. 作为玩家，我想用中文名搜索，以便我不会拼英文
23. 作为玩家，我想用英文名搜索，以便对照游戏原文
24. 作为玩家，我想搜索时不用输完整名字（输"hot"能找到 Hot Dog），以便快速定位
25. 作为玩家，我想搜不到时看到明确的空结果提示，以便知道不是我网络问题

**AI 助手**

26. 作为玩家，我想用自然语言问图鉴内的问题（"蘑菇有什么用"），以便不用自己翻列表
27. 作为玩家，我想 AI 的回答基于图鉴自己的数据，以便答案可信、不会编造
28. 作为玩家，我想问路线类问题时（"今日最佳路线"）AI 给我 B站 上的攻略链接，以便看到真人演示
29. 作为玩家，我想搜索关键词带上**当天的真实日期**，以便找到的是今天的新攻略
30. 作为玩家，我想在该 UP 主当天没有攻略时，得到 B站 全站搜索的结果链接，以便还有备选
31. 作为玩家，我想输入自己的大模型 API Key 就能用 AI，以便不依赖别人替我付费
32. 作为玩家，我想我的 Key 只存在服务端缓存里、不写进代码，以便不会泄露
33. 作为玩家，我想 AI 服务不可用时看到友好提示，以便知道是服务问题不是我的操作问题

**登录与权限**

34. 作为玩家，我想用微信一键登录、不用注册账号，以便零门槛
35. 作为玩家，我想登录状态能保持一段时间，以便不用反复登录
36. 作为玩家，我想未登录也能浏览图鉴，以便先看再决定
37. 作为玩家，我想需要身份的操作在未登录时被明确拦住，以便我知道要先去登录
38. 作为玩家，我想"我的"页面显示我的登录状态，以便确认我是谁

**数据与运维**

39. 作为管理员，我想触发一次采集就把图鉴数据全量更新，以便不用手工录入
40. 作为管理员，我想采集时自动过滤掉 Wiki 上的沙盒测试页，以便图鉴里没有垃圾条目
41. 作为管理员，我想采集时把多值分类字段拆成结构化的标签，以便前端能筛选
42. 作为管理员，我想采集时按公式补全熟食数值，以便详情页能做生熟对比
43. 作为管理员，我想无意义熟食效果（熟了没变化、熟了会爆炸）的条目不被标成可烹饪，以便图鉴不出现空洞条目
44. 作为管理员，我想改完数据后缓存立刻失效，以便用户马上看到修正
45. 作为开发者，我想缓存服务挂掉时接口仍能返回数据，以便演示不会因为环境问题中断
46. 作为开发者，我想在应用启动时预热缓存，以便第一个用户的请求不用等

**验收与协作**

47. 作为项目负责人，我想每一项技术栈都有可当场指出的使用痕迹，以便通过技术栈验收
48. 作为项目负责人，我想每个模块的提交记录能追溯到对应的任务，以便证明分工
49. 作为协作者，我想接口结构在某个时间点冻结，以便我按契约写前端不用反复改
50. 作为协作者，我想数据库账号密码不进版本控制，以便不泄露

## Implementation Decisions

### 数据模型

> **数据模型细节以 `CONTEXT.md` 当前版为准。** 本节只保留决定与理由；字段结构、取值与口径冲突时，一律以 `CONTEXT.md` 为准。

- **一条记录 = 游戏里的一个物品。** 生熟是同一个物品的两种状态，不是两条记录。唯一例外是游戏里本来就独立成物的 `Cooked Bird`。
- 主表只保留需要**筛选或排序**的字段为独立列，其余塞进一个 JSON 列。这个决定成立的前提是**数据量小（130 条）且筛选在应用层做** —— 不是因为 JSON 本身更优。
- **`weight` 必须能表示一位小数且可为负**（数据源实测含 `-2.5`、`7.5`、`12.5`）。
- **分类字段是逗号分隔的多值字符串**（`"Food, Natural food, Berry"`）。因为它要用于筛选，而 `=` 匹配不到、`LIKE` 会误命中，所以**以 JSON 数组形式存储，在应用层筛选**。
- **状态效果以数组存储**，因为效果的数量不固定、且部分效果带附属值（持续时间、延迟生效）。数组能容纳附属值而不需要为每种状态增加列。
- **状态效果是封闭集合**（约 14 种），所以用固定结构而非任意键值对是安全的。

### 缓存

- 图鉴数据在**应用启动时全量预热**到缓存 —— **不绑在用户登录上**。原因：图鉴是纯查询工具，未登录用户也要能浏览；且绑在登录上会导致并发登录重复预热。
- 数据更新（管理员采集后）**删缓存 key 重建**。
- **必须保留"缓存读不到就查库"的降级路径**，因为验收演示不能因缓存服务未启动而中断。

### 持久层

- JSON 列用 MyBatis-Plus 的 `JacksonTypeHandler` 映射。**使用它必须同时开启 `autoResultMap`，否则该字段永远返回 null 且不报错** —— 这是本项目最容易踩的坑。
- JSON 列使用 MySQL 原生 `JSON` 类型（写入时校验格式），不用 `TEXT`（静默存脏数据）。
- JSON 结构用**具体类型**而非 `Map`，让字段名写错在采集阶段就抛异常，而不是等到前端渲染时才白屏。

### 接口契约

- 统一响应包：`{ code, msg, data }`。`code` 为 0 表示成功，401 表示未登录。
- **数据库的 JSON 列不对小程序透传。** 服务端用固定 DTO 组装响应。原因：小程序有版本碎片问题（用户不主动更新），数据库字段可以随便加，但接口响应结构必须是稳定契约 —— 否则改一个 JSON 内的 key 就会让老版本小程序渲染不出来。
- 接口契约在第 5 天**冻结**，之后改动必须通知前端协作者。

### 认证

- 通过小程序的 `js_code` 换 openid 完成登录，签发 token。使用 Shiro 做拦截。
- **Shiro 依赖已引入但尚无 `Realm` 实现，会导致应用无法启动** —— 这是当前阻塞项，必须先补一个最小实现。

### AI 助手

- **问题分两类，走不同路径**：图鉴内问题查后端数据；路线类问题联网在 B站 搜索。
- 路线类问题的链接构造：优先该 UP 主的投稿页；当天无攻略时退回 B站 全站搜索页，**关键词中的日期替换为当天真实日期**。
- **不爬取 B站 搜索页** —— 搜索页反爬严格，取不到数据；只构造链接交给用户点击。演示效果"AI 识别出这是路线问题并给出参考链接"由此成立。
- API Key 由**用户自己提供**，存于服务端缓存，服务端不承担调用成本。
- **成功的回答缓存进缓存服务**（key 用问题文本）。这既是性能优化，也让演示可预热：**演示前先自己问一遍，老师问同样问题时走缓存**。
- **必须提供开关用于降级**：AI 不可用时返回预置回答而非报错，避免演示当场失败。

### 采集

- 采集是**管理员后台的离线功能**，用户永远不触发它，也不在小程序运行时执行。
- 采集的价值不在"下载"，而在**转换**：拆多值字段、按公式与覆盖值算出熟食数值、按判据过滤无意义的熟食条目。
- 熟食数值**在采集时算好落库**（不在应用层算），因为它是展示数据、不随请求变化。

### 范围与验证方式

- 验证方式是**微信开发者工具**（勾选"不校验合法域名"），后端跑在本机。**真机验证不在范围内** —— 它需要一个已备案的 HTTPS 域名，与本项目的时间约束冲突。
- 每一项技术栈（MyBatis-Plus / Redis / Shiro / AI / 小程序 / 采集）都必须留下**可当场指出的使用痕迹**，而不只是"已实现"。

## Testing Decisions

**好测试的定义**：只验证**外部可观察的行为**，不验证实现细节。一个测试不应该因为类名、方法名或内部数据结构变化而失败，只应该在**行为真的变了**时失败。

**采用的接缝：一个 HTTP 冒烟脚本。**

- 它对**运行中的后端**发真实请求，检查状态码与关键响应字段。这是本项目**最高**的接缝 —— 一次请求同时穿过控制器、服务、持久层、缓存、认证。
- **为什么不用单元测试**：本项目真正会踩的 bug 是"JSON 列映射静默失败""缓存没预热""token 没过拦截器"，这三类**只在打真实 HTTP 时才暴露**，单元测试全绿也发现不了。而服务层单测需要 mock 持久层，成本高、覆盖面小。
- **脚本覆盖的检查点**：
  - 列表接口返回非空且带筛选参数时结果收窄
  - 详情接口的 JSON 列字段**有值而不是 null**（这是 `autoResultMap` 的回归保护）
  - 登录接口能拿到 token
  - 受保护接口在无 token 时被拒绝、有 token 时通过（这是 Shiro 的回归保护）
  - AI 接口能返回回答；降级开关打开时仍能返回
- **是否要加更细的测试**：不。现有测试文件里的空 `contextLoads()` 当前是失败的（依赖数据库与 Shiro），保持不动，不用它来衡量覆盖率。
- **这会成为本项目唯一的自动化测试。** 优先把它跑通、跑稳，而不是增加测试数量。

## Out of Scope

- **真机部署与公网发布** —— 需要已备案的 HTTPS 域名，与时间约束冲突。
- **用户收藏 / 收集进度 / 背包** —— 本产品已明确定位为纯查询工具。
- **后台管理界面** —— 采集触发用最简单的方式即可，不做管理 UI。
- **首期以外的分类**（护身符、化妆品、敌人等）。
- **多语言**（除中英文外）。
- **图片自建托管以外的方案** —— 小程序不能直接外链外部站点，图片必须转存。
- **自动化前端测试** —— 开发者工具没有成熟的自动化方案，本项目周期内不投入。

## Further Notes

**参数化名称**：本文档用"缓存服务""采集""认证"等中性说法描述技术组件。项目实际使用的具体框架与版本记录在 `CLAUDE.md`。

**当前阻塞项（按优先级）**：

1. **应用无法启动** —— 认证框架依赖已引入但没有 Realm 实现，整个应用起不来。这是所有其他工作的前提。
2. **数据库账号密码曾在公开仓库的历史提交中** —— 需要清理版本历史并更换密码。
3. **数据源访问受 Cloudflare 拦截** —— 采集有降级方案（离线导入存档）。

**时间约束**：6 天工期，2 名开发者（另有 2 名队友承担不阻塞主线的辅助工作）。逐日排期与降级预案见 `docs/分工与目标清单.md`。

**风险最高的两项**（计划中已各留降级开关）：

- AI 联调（依赖外部服务与可用的 Key）
- 第 3 天的认证联调（缓存 + 认证 + 小程序首次真正联调挤在同一天）
